TabPFN 的使用边界与版本演进

先修：16–19 · 后续：21 实战

TabPFN 的版本信息是动态事实。本节以 2026-10-10 核验的官方仓库和 Models 页面为基准，示范如何记录默认版本、checkpoint、规模、硬件和许可证，而不是把数字永久化。

学习目标

  • 区分 TabPFN-3.5、3.5-Fast、3 及历史版本的记录方式。
  • 理解规模限制与 CPU/GPU 可行性不是同一概念。
  • 检查许可证、checkpoint 下载和在线认证要求。
  • 根据任务条件判断何时不适合使用 TabPFN。

1. 当前核验快照

官方仓库页面显示：默认使用 TabPFN-3.5，也提供 3.5-Fast 和其他版本选择；安装要求 Python 3.10+，分类与回归均有示例。页面同时提示 GPU 推荐、CPU 对中等规模更可行，并给出 checkpoint 相关的行数/特征数参考限制。所有这些内容都必须带核验日期。

API 版本默认构造器和 ModelVersion 选择器。
规模checkpoint 推荐的行数、特征数和类别限制。
资源GPU/CPU、显存、批量预测与延迟。
许可代码许可与模型权重许可分开记录。

2. 适用性决策

  1. 任务是否属于 checkpoint 支持的分类/回归范围？
  2. 样本、特征、类别和内存是否在当前版本建议范围内？
  3. 是否接受首次下载、认证、非商业权重或在线服务条件？
  4. 是否需要极低延迟、海量数据或强可解释性？
  5. 是否有公平基线和资源记录可以比较？

超过官方建议限制时，不能只打开一个忽略保护的参数就宣称“支持”；必须记录风险和实际资源。

每次使用都应沿这五个维度核验当前 checkpoint。

3. 版本记录模板

date=2026-10-09; package=tabpfn; checkpoint=TabPFN-3.5; python=3.13; hardware=record_actual_device; license=record_model_weight_license

当前官方仓库：PriorLabs/TabPFN；模型页面和权重许可需在实验时重新打开。

4. 易错点

误区：README 的一个数字适用于所有 checkpoint。正确理解：限制必须按 checkpoint 和硬件绑定。

误区：代码 Apache 许可等于权重也可商用。正确理解：官方说明代码与权重许可分开。

误区：支持更大规模就一定适合生产。正确理解：延迟、内存、认证、许可证和稳定性仍需评估。

5. 自测

为什么当前版本必须标日期？

官方 API、默认模型、限制和许可可能更新。

规模上限和 CPU 可行性一样吗？

不一样；一个是 checkpoint/保护范围，另一个还取决于硬件和运行时间。

代码许可与权重许可如何处理？

分别查阅并分别记录。

何时不适合直接用本地 TabPFN？

资源、规模、许可、认证或延迟要求不满足时。

如何处理超限数据？

记录官方建议、选择合适 checkpoint/扩展或改用基线，并实测资源。
